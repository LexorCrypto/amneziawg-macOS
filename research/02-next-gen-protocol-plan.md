# План: next-gen / гибридный протокол на базе AmneziaWG 2.0

**Дата:** 2026-07-17 · **Ветка:** `claude/vpn-protocols-research-e4f933`
**Основано на:** [01-vpn-protocols-and-tspu-deep-research.md](01-vpn-protocols-and-tspu-deep-research.md)
**Кодовое рабочее имя:** `AWG-Hybrid` (далее — «протокол»).

> Это **план и дизайн-документ**, а не реализация. Цель — дать инженерно исполнимую дорожную карту, заземлённую (а) в верифицированном research и (б) в реальной архитектуре нашего форка `amneziawg-macOS`. Каждая идея помечена уровнем уверенности и trade-off. Криптоядро WireGuard (Curve25519 / ChaCha20-Poly1305 / BLAKE2s) **не трогаем** — всё живёт на транспортном/обфускационном слое.

---

## 0. Ключевой вывод research в одну фразу

AmneziaWG 2.0 маскирует **хендшейк** (I1–I5 CPS) и **шейпит энтропию/размеры** (S3/S4, динамические H1–H4), но **не делает поток конформным реальному протоколу**. Устойчивое будущее — **слои**: сохранить AWG-UDP-скорость по умолчанию + добавить полнопотоковую TLS/QUIC-маскировку и поведенческую маскировку как опциональные транспорты, плюс **вынести endpoint-стратегию в первый класс** (большинство реальных блокировок 2025–2026 шли по IP/CDN/ASN, а не по параметрам).

## 1. Threat model (конкретно ТСПУ, не GFW)

Что мы принимаем как рабочую модель противника (из Части 2 research; помним caveat «GFW ≠ ТСПУ»):

| Способность ТСПУ | Подтверждено? | Следствие для дизайна |
|---|---|---|
| In-path stateful, терминирует+реконструирует TCP | да (secondary) | Полупротокольная мимикрия недостаточна на TCP; нужна полнопотоковая |
| Fingerprint VPN на **любых** портах | да (secondary) | Смена порта бесполезна; нужна смена **паттерна** |
| SNI-блок (TLS/QUIC), ESNI/ECH заблокированы | да | Нужна фрагментация SNI или SNI whitelisted-домена |
| JA3/JA4 контекстно с ASN | да | TLS-обёртка должна давать аутентичный ClientHello + правильный хостинг |
| Поведенческий детект: >3 параллельных TLS/SNI, flow-профиль | да (blog, 2026) | Мультиплексирование, request/response-шейпинг |
| «Заморозка» TCP после ~15–20 KB к иностранному ДЦ | да (forum) | Разбивать сессии / мимикрия под whitelisted / SSH-носитель |
| Throttling до 2–10% (вероятностный дроп) | да | FEC/устойчивость к потерям (модель Hysteria2) |
| Детект AWG по числу junk-пакетов | да (forum, MTS) | Junk должен быть непредсказуемым, не фиксированным counter |
| Расшифровка QUIC Initial + entropy-порог | **НЕ подтв. для ТСПУ** | Проектировать «на всякий», но проверять эмпирически |
| Active-probing из самого фильтра | **нет** (L2, не генерит трафик) | Cert-gate полезен, но приоритет ниже, чем flow/endpoint |
| IP/CDN/ASN-блок (Cloudflare, Hetzner) | да (forum) | **Endpoint-стратегия — приоритет №1** |

**Вывод:** для ТСПУ по значимости: **(1) endpoint/ASN → (2) поведенческий/flow-профиль → (3) полнопотоковая vs хендшейк-мимикрия → (4) энтропия → (5) active-probing.** Тюнинг junk (то, чем занят AWG 1.x) — в самом низу.

## 2. Архитектура нашего клиента (что придётся трогать)

Поток конфига в форке `amneziawg-macOS` (проверено по коду):

```
.conf ([Interface] jc/jmin/jmax/s1/s2/h1-h4)
   │  парсинг
   ▼
Sources/Shared/Model/TunnelConfiguration+WgQuickConfig.swift
   ├─ interfaceSectionKeys (Set<String>)         ← whitelist ключей секции
   ├─ parse: attributes["jc"] → UInt16 …          ← строка → типы
   └─ serialize: output.append("Jc = …")          ← обратно в .conf
   │
   ▼
Sources/WireGuardKit/InterfaceConfiguration.swift  ← struct с полями Jc…H4
   │
   ▼
Sources/WireGuardKit/PacketTunnelSettingsGenerator.swift
   └─ uapiConfiguration(): wgSettings.append("jc=…\n") … ← UAPI-строка
   │
   ▼
Sources/WireGuardKitGo/api-apple.go
   └─ dev.IpcSet(C.GoString(settings))             ← в Go-ядро amnezia-wg
   │
   ▼
github.com/amnezia-vpn/amnezia-wg v0.1.8 (go.mod)  ← ВСЯ обфускация здесь
```

**Три Swift-точки** (`InterfaceConfiguration`, `WgQuickConfig`, `PacketTunnelSettingsGenerator`) + **`go.mod`** + **UI** (`TunnelEditViewController` / `TunnelDetailTableViewController`). Клиент — тонкий прокидыватель; логика — в Go-ядре. Значит любой новый параметр требует правки **всех трёх** Swift-мест (иначе — ровно баг Amnezia #2219, где S3/S4 терялись между конфигом и UAPI).

## 3. Дорожная карта (этапы, от дешёвого к сложному)

### Этап 0 — Довести форк до AmneziaWG 2.0 (обязательная база, низкий риск)

**Зачем:** наш клиент на `v0.1.8` = AWG 1.x. AWG 2.0 (CPS I1 под QUIC) — единственный **полевым доказанный** рабочий вектор на MTS (апрель 2026). Без 2.0 остальное преждевременно.

Задачи:
1. **Bump Go-ядра** в `Sources/WireGuardKitGo/go.mod`: `amnezia-vpn/amnezia-wg` → версия с поддержкой S3/S4/I1–I5/H-ranges (соответствует `amneziawg-go v0.2.13+`; сверить точный тег/модуль-путь через `go list -m -versions`). Пересобрать `go.sum`.
2. **`InterfaceConfiguration.swift`**: добавить `S3, S4: UInt16?`; `I1…I5: String?`; изменить `H1…H4` с `UInt32?` на строку/диапазон (`String?`, т.к. 2.0 принимает `"123-456"`). Учесть, что старые статические значения — частный случай.
3. **`TunnelConfiguration+WgQuickConfig.swift`**: в `interfaceSectionKeys` добавить `s3, s4, i1, i2, i3, i4, i5`; добавить parse-блоки (для I1–I5 — **без** `UInt16()`-валидации, это шаблонные строки с тегами `<b>/<r>/<rd>/<rc>/<t>`); добавить serialize-блоки.
4. **`PacketTunnelSettingsGenerator.uapiConfiguration()`**: append `s3=/s4=/i1=…i5=/h1=…` в UAPI-строку. **Критично:** гарантировать, что S3/S4/I1–I5 реально доходят до `IpcSet` — это точка бага #2219. Добавить лог/ассерт «UAPI содержит все заданные параметры».
5. **UI**: расширить редактор/детейл-вью новыми полями (или хотя бы принимать их из импортируемого `.conf`, не роняя парс).
6. **Тест-вектор:** прогнать конфиг вида `S3=40, S4=17, I1=<b 0x…>` и проверить, что транспортные данные ходят (а не только хендшейк) — регресс на баг «unknown type 2545529037».

**Trade-off:** нулевой по скрытности сверх апстрима, но это фундамент. **Уверенность: высокая** (механика 2.0 подтверждена 3-0).

**Проверяемый критерий готовности:** AWG 2.0-конфиг с непустыми S3/S4/I1 поднимает туннель с двусторонним трафиком на нашем VPS-хабе (адрес — `infrastructure.md` / LightRAG `infra/`).

### Этап 1 — Anti-behavioral + непредсказуемый junk (низкий риск, высокий ROI)

Бьёт по подтверждённым 2026-детектам, не требуя нового транспорта.

1. **Непредсказуемый junk вместо фиксированного counter.** Полевой факт: MTS матчит **число подряд идущих junk-пакетов**. → рандомизировать `Jc` per-session в диапазоне, варьировать межпакетные интервалы, не слать одинаковый паттерн. (Конфиг-уровень уже сейчас; глубже — в Go-ядре.)
2. **Не открывать >3 параллельных соединения** к одному endpoint/SNI с малой задержкой (триггер июня 2026). Для WireGuard/AWG это менее актуально (одно UDP-«соединение»), но критично для будущей TCP/TLS-обёртки (Этап 2) — там мультиплексировать в один поток, не пулить.
3. **Keepalive/flow-шейпинг:** избегать «непрерывный двунаправленный поток без пауз» (детект VLESS). Вводить джиттер, паузы, разброс размеров, приближенные к request/response-профилю. *(Требует работы в Go-ядре или в прокси-обёртке.)*

**Trade-off:** мелкая латентность/оверхед; скрытность растёт против поведенческого DPI. **Уверенность: средняя** (детекты подтверждены; эффективность контрмер — гипотеза, проверять).

---

### Этап 2 — Гибрид: полнопотоковая маскировка (ядро замысла, высокий риск/выгода)

Отвечает на главную слабость AWG 2.0 (хендшейк-only мимикрия). **Два независимых транспорта, выбираемых по обстановке.** AWG-UDP остаётся default’ом; обёртки включаются, когда UDP душат / нужен TCP/443.

**2A. AWG-over-QUIC/HTTP3 (модель Hysteria2) — рекомендуемый основной гибрид.**
- Инкапсулировать AWG-датаграммы в **настоящий QUIC (RFC 9000) + Datagram Extension**; сервер — полноценный HTTP/3-эндпоинт, прокси-режим за `POST /auth` → `233 HyOK`; неаутентифицированный пробер видит обычный веб-сервер (реальный контент/reverse-proxy).
- Сохраняет UDP-скорость AWG, добавляет полнопотоковую QUIC-конформность и /auth-гейт.
- **Устойчивость к throttling:** взять congestion-модель Hysteria2 (BBR/кастом) + опционально FEC — прямой ответ на «дроп до 2–10%».
- **Trade-off:** там, где ТСПУ душит **весь** QUIC (широкий блок 2022) — не спасёт; нужен fallback 2B.

**2B. AWG-over-TLS-1.3/TCP-443 (модель Reality/ShadowTLS) — fallback, когда UDP/QUIC душат.**
- Обернуть AWG-поток в **настоящий TLS 1.3** к whitelisted-домену, Reality-style (заимствовать идентичность чужого сайта, без своего домена/серта), cert-gated anti-probing (spiderX).
- **Критично из research:** избегать IP/ASN-mismatch (Hetzner + `sni:icloud.com` = детект). SNI прикрытия должен соответствовать хостингу, либо использовать домен на том же ASN.
- Аутентичный ClientHello (взять TLS-стек как naiveproxy/uTLS), иначе JA3/JA4 спалит.
- **Trade-off:** TCP-over-TCP («TLS-in-TLS») — латентность и характерные размеры (частично лечит Vision-подобный режим); наследует поведенческие риски (мультиплексировать, не пулить — см. Этап 1).

**Выбор 2A vs 2B — не «или», а fallback-цепочка:** AWG-UDP → AWG-over-QUIC → AWG-over-TLS/443. Клиент пробует по порядку, запоминает рабочий на данной сети.

**Уверенность: средняя.** Механики Reality/Hysteria2 подтверждены 3-0; их эффективность **против ТСПУ конкретно** — не измерена (open question #4).

### Этап 3 — SNI/handshake fragmentation + connection migration (проверенные примитивы)

Переносимо из GFW-исследований (portability **не опровергнута** — §2.5 research):
1. **Фрагментация SNI-несущего пакета** через несколько UDP-датаграмм (GFW не реассемблит; Chrome+ML-KEM делает непреднамеренно). + приём «префикс dummy-датаграммой перед Initial».
2. **QUICstep connection-migration:** SNI-несущие long-header пакеты — через скрытый канал (например, через сам AWG-туннель), data — прямым путём. Различать по first-bit QUIC-заголовка.
3. **QUIC version-manipulation** как вектор (GFW не декодит v2/negotiation) — проверить, применимо ли к ТСПУ.

**Trade-off:** усложняет клиент/сервер; выигрыш — только если ТСПУ действительно парсит SNI из QUIC (open question #1). **Делать после эмпирической проверки threat-model.**

---

### Этап 4 — Endpoint & moving-target стратегия (приоритет по факту — высокий)

Research показал: большинство блокировок 2025–2026 — по IP/CDN/ASN, не по протоколу. Значит:
1. **Диверсификация ASN/хостинга:** не только Hetzner/DO/Cloudflare (массово блокируются). Рассмотреть провайдеров, где ASN-mismatch не палит выбранный SNI-прикрытия.
2. **SSH-носитель:** SSH/SFTP устойчиво не трогают (подтверждено многократно). Опция «AWG/прокси поверх SSH» или CPS-мимикрия I1 под SSH-баннер — практичный low-hanging fruit.
3. **Резидентные/CDN-совместимые выходы** там, где ТСПУ не давит ДЦ-сети выборочно.
4. **Мат-ограничение ротации (Block-A-Mole):** при burn-rate **β>1** доступность ≤ **1/β** независимо от скорости ротации. → одна ротация IP не выигрывает; нужна экономика «создание эндпоинтов дешевле, чем их сжигание цензором». Для ТСПУ-модели (μ/λ_a≈3.75, медленнее GFW) порог достижимее, но не бесплатен.

**Trade-off:** операционная сложность (много эндпоинтов, автоматизация). **Уверенность: высокая** по важности вектора, средняя по конкретной экономике.

## 4. Что НЕ делать (dead ends из research)

- ❌ **Только рандомизация junk / тюнинг Jc-Jmax** — MTS уже детектит по числу junk; это косметика.
- ❌ **Только смена порта** — ТСПУ фингерпринтит на любых портах.
- ❌ **Только ротация IP без экономики** — β>1 ⇒ доступность ≤ 1/β.
- ❌ **Reality-over-TCP с connection pooling** — прямой триггер «>3 параллельных TLS» (деградировал в 2026).
- ❌ **Hetzner + mismatched SNI** — ASN-mismatch детект.
- ❌ **Полагаться на entropy-обфускацию как главный щит** — тезис про entropy-band не подтверждён, но «случайный поток заметен» как класс — реальный риск; entropy не первичный вектор, но и не решённая проблема.

## 7. Открытые вопросы (блокируют выбор P1/P2)

Перенесены из research — все проверяемы на нашей инфраструктуре:
1. Парсит ли ТСПУ QUIC Initial / гоняет ли entropy — или fingerprint+поведение+IP/ASN? (определяет ценность Этапа 3 и 2A vs 2B)
2. Полевой статус середины 2026: AWG 2.0 / Reality / SS-2022 / Hysteria2 против ТСПУ.
3. Меняет ли S4-padding + динамические H1–H4 энтропию/размеро-тайминги достаточно?
4. Переживает ли CPS-мимикрия **stateful**-DPI или нужна полнопотоковая маскировка — и какой ценой latency/throughput?
